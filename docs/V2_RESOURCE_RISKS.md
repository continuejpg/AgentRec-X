# V2 资源与启动风险验收

## 1. 为什么单后端 Profile 仍构建全部三个引擎（如实解释 ✓）
`_build_fusion_engines`（`recommendation/api/app.py:200-300`）在构建 `FusionInferenceEngine` 前**无条件**创建
`sequential` + `two_tower` + `lexical`（`api/app.py:215/219/228-231` ✓），因为该引擎的构造函数契约要求三个
source 对象存在 ✓；本轮获批范围只允许**配置层**新增 profile ✓，**未**允许改引擎生命周期 ✗。
⇒ 因此：**profile 只决定"哪些 source 参与排序"** ✓，**不决定"哪些模型被加载"** ✗。
**不得**宣称模型加载已按 profile 隔离 ✗（本轮报告中已按此措辞 ✓）。

## 3. 是否满足 V2 资源验收标准
V2 文档**未**给出显式数值内存门槛 ✗ ⇒ 无法给出"达标/不达标"的正式判定 ✗；
以工程判断：**单后端 profile 的在线部分**（不含离线参考引擎）历史实测约 **0.6–0.9 GB** ✓
（SASRec 加载后 498.6 MB / 峰值 636.1 MB ✓；Two-Tower 加载后 704.5 MB / 峰值 872.4 MB ✓ —— 见 Gate B-1/B-2 ✓），
**满足单实例部署** ✓；**离线核对与在线服务同进程运行**是本轮验收驱动的**临时叠加** ✗，不是生产部署形态 ✓。

## 4. 并发与启动稳定性风险
* **启动**：缺省 profile 与单源 profile 均能正常启动与关闭 ✓；未知名启动即失败（fail-closed ✓）。
* **并发**：本轮为**单进程顺序**请求 ✗，**未**做并发压测 ✗（**不宣称**并发性能 ✓）；
  真正的并发验收需单独授权（含线程/内存与 lexical 索引的读并发的评估 ✗）。
* **内存余量** ⚠️：同进程叠加时余量 <1 GB ⇒ 高并发或更大 K/更多 source 存在 **OOM 风险** ⚠️。

## 5. 精确阻塞与最小修复方案（**不擅自重构** ✗）
* **阻塞 R1**：profile 不裁剪引擎加载 ✗（内存冗余 ⚠️）。**最小修复**：让 `_build_fusion_engines`
  按 `config.sources` **惰性构建**缺失的 source 对象，并为 `FusionInferenceEngine` 增加
  "缺失 source 视为不可用"的显式契约 ✓（属**引擎生命周期**变更 ✗ ⇒ **需批准** ✗）。
* **阻塞 R2**：验收驱动把离线参考与在线服务放在同一进程 ✗。**最小修复**：验收脚本改为**两进程**
  （在线 API / 离线参考分离 ✓），仅影响测试驱动 ✓（**无需批准** ✗，但本轮已按序进程隔离模型生命周期 ✓）。
* **阻塞 R3**：并发性能无证据 ✗。**最小修复**：单独一轮并发验收（限并发、记录 p95 与 RSS ✓），需授权 ✓。
