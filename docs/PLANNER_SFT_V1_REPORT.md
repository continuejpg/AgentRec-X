# Planner Action SFT v1 — Reproducible Qwen3.5-9B Experiment

## 1. Decision boundary: what Qwen actually controls

Verified in the existing Planner contract, executor and direct task harness:

- Qwen outputs only `{"action", "arguments", "rationale"}` with
  `ASK | RETRIEVE | RERANK | FINALIZE`.
- Qwen never emits a product `item_id`; FINALIZE has no item argument.
- The trusted executor/scorer/DecisionGate determines the selected product after FINALIZE.
- RERANK changes candidate ordering/eligibility inspection, but does not give the planner an
  item-selection field.
- Qwen can indirectly change the eventual candidate pool through the RETRIEVE `query` and
  `source_policy`, and can choose whether to RERANK/FINALIZE.

Consequence: **action SFT can improve action/query policy, but cannot directly repair a
Top-1 selection error.** No Planner Action Schema was invented to make selection trainable.

Observed example: SFT `p14e2_lite_0049` produced a different RETRIEVE query, ending with a
one-item unverified pool; the Base query had acceptable candidates in the pool. This is a
model-controllable query/action effect, not direct item selection.

## 3. Training Framework Reuse

Reused the existing `training/planner_sft/train_lora.py` stack:

- Transformers `Trainer`;
- PEFT `LoraConfig` / `get_peft_model`;
- completion-only labels;
- existing Qwen3.5 `Qwen3_5ForCausalLM` and tokenizer/chat template;
- no TRL or Unsloth installed; no new framework introduced.

Minimal additions for this experiment:

- `--load-in-4bit` QLoRA switch;
- `--limit-train`, `--max-steps` smoke controls;
- `--save-total-limit`;
- `--run-name`.

Training data are real `PlannerObservation` requests reconstructed by replaying successful
traces through the actual executor. Chat rows use the current planner system prompt and the
current Planner Action contract.

## 8. Failure and Overfitting Cases

### `p14e2_lite_0042` — real SFT regression, contract error

SFT emitted a legal final JSON action at a step where `allowed_actions` excluded FINALIZE;
the executor raised `PlannerContractError: FINALIZE is not allowed now`. Its rationale
relied on `m5_state.candidate_count=20` while the observation's `candidate_ids` was empty.
This is a **contract/state-attribution failure**, not a JSON parser failure.

### `p14e2_lite_0049` — query/candidate-pool regression

SFT RETRIEVE query led to a one-candidate pool that was not verified. Base recovered
acceptable candidates and succeeded. This shows the model can affect eventual selection
through its query, but it still cannot directly emit the selected item.

### `p14e2_lite_0051` — unchanged selection failure

Both Base and SFT had verified candidates in the pool and both selected the wrong product.
SFT did not fix this; this is consistent with selection not being a Planner Action field.

### Ceiling effect

Base and SFT both scored 10/10 on the independent eval100 subset. That subset is too easy
for this comparison; the only observed 30-task changes were regressions on dev tasks.

## 10. Retain the Adapter?

**Do not adopt the SFT adapter as the default Agent planner.**

Reasons:

- no end-to-end gain on the 30-task suite;
- two new failures on dev tasks;
- held-out set is saturated at 10/10 for Base, so no positive evidence;
- action val improves, but the old rule-derived adapter already reached 93.9%;
- QLoRA was required after BF16 OOM and adds fidelity risk.

The adapter is retained only as an **experimental artifact**:


Base model was not overwritten. No merged 9B BF16 model was saved.

## 11. DPO / Agent RL?

Not yet.

- The current SFT labels are action-imitation labels; there is no preference-pair or
  per-action reward signal.
- The product selection is Gate-controlled, so a DPO pair on final item quality would not
  cleanly credit the planner.
- A useful reward would need to separate candidate recall, query quality, action efficiency,
  and final Gate outcome.
- Build DPO/RL only after an independent, non-ceiling evaluation set and a model-controlled
  selection target exist.
