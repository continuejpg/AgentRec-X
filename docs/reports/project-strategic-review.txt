AGENTREC-X -- PROJECT-LEVEL STRATEGIC REVIEW
====================================================================================================

  ANALYSIS ONLY.  No code change, no training, no benchmark, no fusion, no commit, no push.
  Purpose: what remains to COMPLETE AgentRec-X as a project, rather than to keep optimizing
  TIGER.  Every status below cites a concrete artifact; nothing is inferred from the recent
  TIGER experiments except where stated.

  HEADLINE: the project is far more complete than the recent TIGER loop suggests.  The
  mainline recommendation backbone and the Agent control plane are implemented, tested and (for
  the retrieval arms) measured.  Three things block research-completion, and none of them is a
  TIGER experiment:
    1. DURABILITY: the accepted state is unpushed and partly uncommitted -- it exists on one host.
    2. UNCERTAINTY: every accepted attribution is a point estimate; the project's own handoff
       document lists this as its #1 open step, and Step 2.8b showed the accepted fusion gain
       is inside cohort noise.
    3. THE THESIS: the project has never measured the LIVE agent policy against the fixed-fusion
       baseline.  The only adaptive number in the canonical benchmark is a deterministic rule
       stand-in, and it LOSES to fixed fusion.

4. THESIS AUDIT (implementation is NOT evaluation)
====================================================================================================
  * bounded adaptive agent behavior              SUPPORTED (implemented + unit-tested)
      recommendation/control/loop.py with budgets/stopping; tests/test_llm_agent_policy.py,
      tests/test_evaluation_agent_plane.py; runs through a real control plane in
      experiments/agent_evaluation_smoke.py.  But 'bounded' is asserted by tests, not measured
      as a distribution over real runs.
  * heterogeneous tool use                       PARTIALLY SUPPORTED
      Five tool/capability kinds exist (history recommender, catalog search, similar item, two tower,
      tiger) and the plane dispatches per action.  Measured multi-source behavior exists ONLY as
      the fixed-fusion and rule-stand-in arms, never as a live policy choosing tools.
  * agent decision authority                     SUPPORTED (structurally)
      The policy proposes; ActionValidator + ValidatedAction give the controller authority; a
      proposal cannot carry history, a candidate identity, or a tool name (schemas.py).
  * trusted-code truth authority                 STRONGLY SUPPORTED
      GroundingVerifier owns identity; unknown identities become UNGROUNDED audit entries and never
      candidates; no parent_asin crosses the backend boundary.  Qualified end-to-end in Step 2.7
      on real TIGER output (0 ungrounded, 0 fabricated, 20 000/20 000 cohort identity).
  * adaptive source selection                    EVALUATED AND NEGATIVE (rule stand-in only)
      runs/phase5_benchmark_public/arms.json: agent_selected 0.01180 vs fixed_fusion 0.01435;
      ARCHITECTURE s25 states 'threshold-based adaptive selection loses to fusing everything'.
      This is a real, honestly-reported negative result - but for a RULE, not the LLM policy.
  * constraint handling                          IMPLEMENTED, NOT EVALUATED AT SCALE
      constraint_eligibility.py + ConstraintReport; ARCHITECTURE s25 states evidence is a local
      fixture, so an uncovered constraint stays UNKNOWN.  No measured constraint-success rate.
  * failure recovery                             IMPLEMENTED, PARTIALLY MEASURED
      Failure isolation is now proven for a candidate source (Step 2.7 Q5: 9 failure modes,
      source-local, ledger untouched).  Agent-loop-level recovery was measured only in the smoke
      (per-component failure attribution, Phase-4 repetition 2 of 8 failures).
  * benefit over fixed retrieval/fusion baselines UNSUPPORTED
      For a rule policy the answer is measured and negative.  For the live LLM policy there is NO
      measurement at all at cohort scale.  This is the project's central open claim.

  VERDICT ON THE THESIS: the *architecture* thesis (trusted code owns truth; the model proposes)
  is well supported and enforced by tests.  The *performance* thesis (an adaptive agent beats a
  fixed fusion of the same sources) is currently CONTRADICTED by the only measurement that
  exists, for a rule stand-in, and UNMEASURED for the live policy.  Any project-completion claim
  must resolve that, positive or negative.

6. DIMINISHING-RETURN LOOPS
====================================================================================================
  For each chain: what NEW project-level claim would the next experiment enable?
  * BF16 root-cause work
      NONE.  Gate D passed under FP32 remediation; the remediation is accepted and the canonical
      checkpoint is qualified.  A root cause would not change any accepted number.
      -> DEFER
  * TIGER hyperparameter tuning
      NONE.  TIGER is frozen and measured; a better TIGER would invalidate the frozen 0.01385 and
      the H7/H8 evidence while facing the same within-noise fusion outcome.
      -> DEFER
  * candidate-depth tuning
      NONE.  Step 2.8b already ran the one preregistered common-depth control; direction held, the
      mechanism changed, and s3 forbade choosing a policy by its test result.
      -> DEFER
  * RRF constant tuning
      NONE beyond 'was c=60 suboptimal?', which is a local knob on an effect that is inside noise.
      -> DEFER
  * weighted fusion
      ONE: 'do unequal weights beat equal weights?'.  But the accepted-policy base effect is not
      established, so weights chosen on test would fit noise.  It becomes answerable only AFTER the
      uncertainty milestone, and then only with validation-selected weights.
      -> DEFER (until after M2; then a separate pre-registered milestone)
  * score calibration
      NONE.  The repository's design explicitly refuses to compare score scales across sources
      (CandidateProvenance keeps score_kind precisely so scales are never conflated).  Calibration
      would require repealing a deliberate design invariant to chase a within-noise gain.
      -> DEFER (and arguably against the design)

  STRUCTURAL OBSERVATION: the last several milestones have all been local optimization on ONE
  retrieval source while the project's central agent claim has never been measured.  That is the
  definition of a diminishing-return loop and is the reason for the critical path below.

9. RECOMMENDED TIGER STOP POLICY
====================================================================================================
  RECOMMENDATION: KEEP TIGER AS A QUALIFIED OPTIONAL SOURCE.  Do not continue TIGER/fusion
  research; do not remove TIGER from the mainline.

  Why not continue: every remaining TIGER lever (depth, RRF constant, weights, calibration,
  tuning) is local optimization that enables NO new project-level claim, the accepted fusion
  gain is inside cohort noise, and the project's central unmeasured claim is about the AGENT,
  not the retriever.  Continuing would be the diminishing-return loop Section 6 identifies.
  Why not remove: TIGER is the only delivered generative retriever, it is fully qualified at the
  CandidateSource boundary (an asset the thesis milestone should exercise), its 138-user oracle
  complementarity is the largest single addition measured, and keeping it costs ~1 ms/call of
  source-layer overhead with a frozen 1.33 h batch path.  Removal would delete real, previously
  accepted evidence for no project benefit.
  Why 'optional': it is not on the critical path.  M3 should test the agent policy over the
  STRONGEST source set (which includes TIGER), and that is use of frozen TIGER results, not new
  TIGER research.
  This recommendation is NOT executed in this milestone.
