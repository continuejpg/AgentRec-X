2. CANDIDATESOURCE ARCHITECTURE
====================================================================================================
  recommendation/control/tiger_source.py
    TIGER_SCORE_KIND      == "tiger_sid_sequence_logprob"
    TigerProposal         per-candidate record: parent_asin, rank, score, semantic_id, item_id,
                          retrieval_mode, checkpoint_sha256, sid_artifact_sha256, resolver,
                          source name/version
    TigerSourceTool       source=CandidateSource.TIGER; score_kind=TIGER_SCORE_KIND;
                          propose(*, arguments, limit, history) -> [(parent_asin, rank, score)]

  It mirrors TwoTowerSourceTool exactly at the seam: it never grounds an identity, never
  chooses its own history, never mixes its scores with another source's, and never promotes a
  retrieval status.  Everything identity-related stays with the trusted plane.

  The full provenance list required by section 4 is retained in two places: the complete
  record lives on the tool (last_proposals), and the mode plus artifact hashes ride into the
  ledger through the shared source_query field as a compact token, because the shared
  provenance schema deliberately has no TIGER-specific field and none was added.

====================================================================================================
3. EXACT TRUST-BOUNDARY MAPPING
====================================================================================================
  TIGER side (proposes only)                     AgentRec-X side (decides)
  -------------------------------------------    ---------------------------------------------
  history SID encoding                          trusted history read by the plane
  generator forward scoring                     -
  constrained decoding / prefix expansion       -
  candidate SID generation                      -
  token path -> integer item id (trie leaf)     -
  -                                             item id -> parent_asin (frozen mappings)
  -                                             GroundingVerifier membership decision
  -                                             CandidateLedger provenance + dedup
  -                                             constraint feasibility / presentability
  -                                             ranking, tie-breaking, metrics

  A TIGER Semantic ID is a PROPOSAL.  It becomes a candidate only after trusted code resolves
  it to a parent_asin and the GroundingVerifier accepts it.  TIGER never acquires truth
  authority, and no identity mapping is ever inferred by a model.

====================================================================================================
4. TIGER OUTPUT -> parent_asin PATH
====================================================================================================
  1. the plane hands the tool the run's trusted history (never the tool's own choice)
  2. the tool maps parent_asin -> item_id through the engine's trusted mapping
  3. the engine returns proposals carrying item_id and semantic_id, plus the artifact hashes
  4. the tool validates every field and returns (parent_asin, rank, score) triples
  5. the plane calls GroundingVerifier.record(...), which is the only supported path into
     the ledger; an unknown identity becomes an UNGROUNDED audit entry, never a candidate
  6. only grounded identities reach the renderable candidate set

  The certified artifact deliberately carries NO parent_asin (boundary rule 19.2(1)); the
  frozen trusted mappings re-attach identity on the AgentRec-X side, which is exactly what the
  qualification exercised against real H7 output.

  Recommended: a pre-registered FUSION milestone, now that a source has been qualified on
  boundary grounds.  Concretely, and in this order:

  1. Pre-register the fusion question and its criterion BEFORE any fused number exists.  The
     natural primary quantity is oracle-union coverage after fusion, to be compared against the
     already-frozen S u T = 460 and S u T u G = 598 at K=10.
  2. Start with rank-only fusion (RRF), because rank is the one cross-source quantity the ledger
     already preserves verbatim for every source.  Weighted or learned fusion would require
     cross-source score calibration, which is a separate decision with its own risks.
  3. Reuse the existing two-tower_fusion_controls harness so the controlled contrasts (each
     source alone, RRF pairs, RRF triples, and the 'adding TIGER' contrast) are produced by one
     evaluator with one protocol.

     changed to consider TIGER - policy change is a further, separate step.

  NOT recommended: enabling TIGER in the runtime now, tuning TIGER from the metric, or
  reopening BF16 forensics.
